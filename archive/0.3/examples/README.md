# Fictional v0.3 record shapes

The current folder includes semantic records, signed-envelope shapes for offer/status interactions and two recipient-specific admission declarations. All retain fictional proof references. [A2A construction templates](a2a/README.md) show native carriage with explicit placeholders and are not complete signed examples.

These files illustrate publication through accepted-offer status. They are design-review material, not a running demonstration, passing protocol test suite, real promises, live authority evidence, or signed agreements. All identities, policies, timestamps and records are fictional. `illustrative-native-proof.json` contains no signature. Proof references use an explicitly unimplemented reserved `example.org` profile URI; they do not claim that a particular native suite is compatible with this digest envelope. **No proof in this folder can establish authenticated authorship.** A real selected existing proof suite must authenticate exact record content, issuer and scope.

Read the publication records, requester/researcher intents, researcher offer options, requester offer, candidate, two adoptions, accepted offer, notice events and status snapshots in that order. An intent includes the emitter's qualified promise to disclose its interest; it does not promise the sought fulfillment or a purchase. An offer contains issued qualified own promises and separately requested counterpart promises. The extended option remains independent when the standard option is revised. `selection-constraints.json` describes the fictional capacity/exclusivity policy.

The declared originating intent pins `agent:requester` as coordinator. No timestamp election or buyer-role rule chooses it. Both principals' nonzero refusal durations and notice targets are in the candidate before adoption. Agent finalization produces an immutable `accepted_offer` with pending windows. A missing notice supplies no start or deadline. Each fictional notice starts its window at `max(finalized_at, notice_at)`. The researcher refusal is admitted exactly at its deadline and therefore wins. The final example status is `refused`; this accepted object cannot later become usable through a reopened window.

This example uses two offer records in its final bundle, but the schema permits direct acceptance of one offered option and permits additional compatible options under the selection constraints. No reciprocal offer is mandatory. Exact adoption can confirm previously issued own promises or issue qualified requested-own actions; the candidate alone never issues the counterpart's behavior. An adopter may instead assent without taking on a separate substantive performance promise: its `adopted_own_promise_ids` is then empty, while capability and authority evidence for adoption remain required. The candidate does not manufacture a second service obligation. The two agents may share one principal: refusal-window descriptors, observations, and current policy/authority checks must each cover every distinct principal exactly once, keyed by `principal_id`. JSON `uniqueItems` alone does not enforce that identity-based rule.

`explicit-promise.json` illustrates the generic promise record outside an agreement. It introduces no special standing-service-promise category. Withdrawal of one alternative is a separate authored event.

Draft 0.3 adds exact `promise_bindings` to the candidate. Both example actions resolve their previously issued selected offers. `requester-invitation.json` shows a scoped optional invitation grant; this example's published policy already permits its first offer, so the invitation is not a required extra handshake. `researcher-clarification.json` is a question, not an offer. `requester-contact-close.json` stops discretionary contact without withdrawing separate commitments. These supplemental records illustrate shapes rather than asserting a single executed transcript.

`offer-interaction-request.json` and its receipt demonstrate recording an offer without adopting it. The finalization interaction binds the candidate and returns the accepted object with its windows still pending. The status interaction returns the existing refused snapshot. Each pair binds exact subject/request digests, recipient, admission basis and stable operation identity. The admission declarations expose finite illustrative pools for negotiation and control, each recipient's shared scope, no automatic replenishment and bounded reply size. Their referenced policy/evidence documents remain fictional and do not implement those mechanisms.

An initiating offer needs no earlier intent or generic promise. It may identify itself with `origin = {self_origin: true, record_kind: "offer", record_id, originator_agent_id, originator_principal_id, coordinator_agent_id}` and no circular self digest. The referenced ID and identities must match that offer's authenticated author and top-level ID. Only an initiating offer may use this marker. Later offers and every candidate, adoption and accepted object use the normal digest-bearing reference to the complete first offer. Self-origin markers are not accepted on downstream formation records.

The schema also permits `refusal_windows_closed` and `unresolved` snapshots. A closed-window claim requires current authoritative evidence for both notices, current policies/authority, and no admitted refusal. The schema cannot validate those facts or the strict clock ordering. No status establishes execution permission, native order authorization, payment, delivery, or result acceptance.

`checks/validate.py` checks the schema, record shapes and local references only. It does not run behavior, state-machine, cryptographic, A2A, capability, authority, or payment tests. The fixture digests use a restricted ASCII/integer serialization equivalent to JCS for these authored values; the helper is not a general JCS implementation. `signed_payload_digest` covers the entire record excluding its top-level `proofs` array. The selected native proof suite must authenticate that digest together with issuer and scope in a real implementation.
